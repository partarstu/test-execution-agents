# Implementation Plan: Avaje Inject DI Integration

**Created**: 2026-03-06
**Updated**: 2026-03-24
**Status**: Phase 12 complete — UI helper & utility classes refactored (UiElementRefinementHelper, UiElementDialogHelper, ImageUtils, BoundingBox, ProcedureKnowledgeCollectionDialog, ExistingProcedureLookupDialog, AgentCardProducer). Architecture decision documented: static utility classes with no injectable dependencies are excluded from DI and remain as static utilities; `UiCommonUtils` reverted to pure static (removed erroneous `@Singleton`/`@Inject`/instance field introduced in Phase 12).

## 1. Objective

Integrate Avaje Inject (v12.5-RC1) as the dependency injection framework across all 3 modules (`agent_core`, `ui_test_execution_agent`,
`api_test_execution_agent`), replacing static factories, static config, and manual singleton management with compile-time DI-managed beans.

## 2. Technical Dependencies

Three avaje-inject artifacts must be added, all at version `12.5-RC1`, managed via `<dependencyManagement>` in the parent POM:

- **`avaje-inject`** — runtime library (compile scope in each module)
- **`avaje-inject-generator`** — compile-time annotation processor (provided/optional scope; no `annotationProcessorPath` config needed when
  `maven.compiler.proc=full` is set in parent POM properties)
- **`avaje-inject-test`** — test utilities (test scope in each module)

All three modules declare the runtime and processor artifacts. The `maven.compiler.proc=full` property in the parent POM properties section
enables the processor automatically.

Verify that `ServicesResourceTransformer` is already present in the shade plugin config — no change needed there (confirmed present in both
ui and api module POMs).

## 3. Architectural Design

### Design Patterns

- **Factory Method via `@Factory`/`@Bean`**: Replace static factory classes with DI factory beans that produce third-party objects (
  LangChain4j models, Neo4j driver, singleton agents)
- **Singleton Scope**: All stateless services, config beans, shared resources, and stateless agents become `@Singleton`
- **Constructor Injection**: All dependencies declared via constructors — immutable, testable, explicit
- **Extracted mediator to break cycles**: `ProcedureKnowledgeCollectionService` is introduced to eliminate the circular dependency between
  `StepExecutionOrchestrator` and `KnowledgeBasedExecutionOrchestrator` (see §3.4)

### Annotation Placement Rules (Quick Reference)

| Annotation                | Placement                                                           | Effect                                                                                                                                                                                                                       |
|---------------------------|---------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `@Singleton`              | On the **class declaration**                                        | Registers the class as a singleton bean. Avaje auto-discovers and manages its lifecycle                                                                                                                                      |
| `@UiAgentRequestScope` / `@ApiAgentRequestScope` | On the **class declaration**                                 | Custom scope annotations (meta-annotated with `@Scope` + `@InjectModule`). Registers the class as a request-scoped bean. A fresh instance is created in each child `BeanScope` built with `.modules(new UiAgentRequestScopeModule(...))` / `.modules(new ApiAgentRequestScopeModule(...))`. Can inject `@Singleton` beans from the parent scope and other beans from the same custom scope |
| `@Factory`                | On the **class declaration**                                        | Marks a class as a producer of beans via `@Bean` methods. The class itself is NOT a bean — only its `@Bean` methods produce beans. Constructor parameters of a `@Factory` class are auto-injected by avaje                   |
| `@Bean`                   | On a **method** inside a `@Factory` class                           | The method's return value becomes a managed bean. Add `@Singleton` alongside `@Bean` if only one instance should exist (i.e., `@Bean @Singleton`). Method parameters are auto-injected by avaje (method parameter injection) |
| `@Bean` method parameters | On **method parameters** of `@Bean` methods                         | Avaje injects these at bean-creation time. This is independent from constructor injection and does NOT trigger circular dependencies with the `@Factory` class's constructor                                                 |
| `@InjectModule`           | On a **`package-info.java`** file                                   | Declares cross-module `provides`/`requires` so avaje validates wiring at compile time                                                                                                                                        |
| `@PostConstruct`          | On an **instance method** (no args, void return)                    | Called by avaje after the bean is fully constructed and all dependencies injected                                                                                                                                            |
| `@Inject`                 | On a **constructor** (only needed when multiple constructors exist) | Tells avaje which constructor to use. When a class has exactly one constructor, `@Inject` is optional — avaje uses it automatically                                                                                          |
| No annotation needed      | **Constructor parameters** of `@Singleton` or `@Factory` classes    | Avaje automatically injects all constructor parameters by type. This is **constructor injection** — declare the dependency as a constructor parameter and avaje resolves it                                                  |

**Injection pattern summary:**

- **`@Singleton` class**: annotate the class → declare dependencies as constructor parameters → avaje injects them automatically
- **`@Singleton` record**: annotate the record → canonical constructor parameters become injection points → avaje calls
  `new MyRecord(dep1, dep2)` with resolved beans. Works because avaje uses compile-time code generation, not runtime proxies — `final` is
  not an issue
- **`@Factory` class**: annotate the class → declare shared dependencies as constructor parameters → produce beans via `@Bean` methods →
  method parameters are also auto-injected
- **`@UiAgentRequestScope` / `@ApiAgentRequestScope` class**: annotate the class → declare dependencies as constructor parameters → avaje injects
  them within the request child scope. Can inject both `@Singleton` beans (from parent scope) and other request-scoped beans (from child
  scope). Created per-request as a fresh instance; cleaned up when the child `BeanScope` is closed
- **`@UiAgentRequestScope` / `@ApiAgentRequestScope` `@Factory` class**: annotate with both the scope annotation and `@Factory` → produce `@Bean`
  methods that are also request-scoped. Constructor parameters are auto-injected from the request child scope (or parent scope for
  singletons)
- **Non-DI classes** (value objects, Swing dialogs with EDT lifecycle, objects requiring multiple distinct instances per request with
  different config): callers create via `new` and pass dependencies as constructor parameters
- **Static utility classes** (pure collections of stateless helper functions with no injectable dependencies — e.g., `CommonUtils`,
  `PromptUtils`, `BoundingBoxUtil`, `HtmlUtils`, `UiCommonUtils`, `ImageMatchingUtil`): remain as static utilities. DI adds no value
  when there is nothing to inject; converting them would force unnecessary injection across all callers without any testability or
  lifecycle benefit.

**Guiding principle:** Use DI everywhere it is applicable. Avoid mixing DI and non-DI initialization patterns. Only fall back to manual
`new` when the object's lifecycle is fundamentally incompatible with DI (Swing dialogs created on the EDT, value objects with per-instance
data like `BoundingBox`, objects where multiple distinct instances with different config exist per request like
`DefaultToolErrorHandler`). Static utility classes with no injectable dependencies are also excluded — they remain as static utilities.

### 3.5 Request Scope Architecture

A custom `@BaseAgentRequestScope` annotation in `agent_core` along with specific `@UiAgentRequestScope` and `@ApiAgentRequestScope` annotations defines per-request beans. The annotation
declares external runtime dependencies via `@InjectModule(requires = ...)` so that avaje generates a module constructor that accepts them.

**Core module scope annotation** (in `agent_core`):

```java
@Scope
@InjectModule(requires = {TestCase.class})
public @interface BaseAgentRequestScope {}
```

**UI module scope annotation** (in `ui_test_execution_agent`):

```java
@Scope
@InjectModule(requires = {VisualState.class})
public @interface UiAgentRequestScope {}
```

`TestCase` is NOT in `requires` here — it is already provided by the previously-wired `BaseAgentRequestScopeModule` in the same child scope. Per avaje docs, beans from previously-wired modules are available to subsequently-wired modules, so `@UiAgentRequestScope` beans can inject `TestCase` without it being declared here.

**API module scope annotation** (in `api_test_execution_agent`):

```java
@Scope
@InjectModule(requires = {})
public @interface ApiAgentRequestScope {}
```

`TestCase` is NOT in `requires` here — same reason as above.

At compile time, avaje generates `UiAgentRequestScopeModule` and `ApiAgentRequestScopeModule` classes. The generated constructors accept the
external dependencies declared in `requires`. At the entry point of each server request, a **child `BeanScope`** is created:

```java
TestCase testCase = testCaseExtractor.extractTestCase(receivedMessage).orElse(null);
// ... early return if null ...

try (BeanScope requestScope = BeanScope.builder()
        .parent(appScope)
        .modules(new BaseAgentRequestScopeModule(testCase), new UiAgentRequestScopeModule(new VisualState(captureScreen())))
        .build()) {
    // All @UiAgentRequestScope beans auto-wired within this scope
    // All @Singleton beans inherited from appScope
    var screenRecorder = requestScope.get(ScreenRecorder.class);
    screenRecorder.beginScreenCapture();
    // ... entire request runs within this scope ...
}
```

The existing child `BeanScope` in `executeWithKnowledgeFlow()` is **eliminated** — replaced by this single request scope at the top of
`executeTestCase()`.

**Scope visibility rules:**

- `@UiAgentRequestScope` / `@ApiAgentRequestScope` beans can inject `@Singleton` beans from the parent scope (automatically — custom scope beans
  are allowed to depend on any bean in the default scope implicitly)
- `@UiAgentRequestScope` / `@ApiAgentRequestScope` beans can inject other beans from the same custom scope
- `@Singleton` beans **cannot** inject request-scoped beans (parent cannot see child). Singletons that need per-request data receive it
  via **method parameters** (e.g., orchestrators receive `UiTestExecutionContext` as a method parameter)
- `TestCase` and `VisualState` are **external dependencies** declared in `@InjectModule(requires = ...)` and passed via the generated
  module constructor

**Request-scoped beans by category:**

| Category | Beans | Module |
|---|---|---|
| Per-request mutable context | `TestExecutionContext`, `UiTestExecutionContext`, `ApiContext`, `ExecutionStateTracker` | ui / api |
| Per-request lifecycle | `LogCapture`, `ScreenRecorder` | core / ui |
| Per-request tools (API) | `ApiRequestTools`, `ApiAssertionTools`, `TestContextDataTools` | core / api |
| Per-request agents (API) | `ApiTestStepActionAgent`, `ApiPreconditionActionAgent` (depend on request-scoped API tools) | api |

**Parent scope (`@Singleton`) — infrastructure + stateless beans:**

- Configs: `AgentConfig`, `UiTestAgentConfig`, `ApiTestAgentConfig`
- Infrastructure: `ModelFactory`, `ChatModelEventListener`, `TestCaseExtractor`, `Neo4jFactory`, `Driver`, `Neo4jRepositorySupport`,
  `EmbeddingService`, `AbstractServer`, `AgentExecutionResource`, executors
- All 7 repositories (stateless query executors)
- All knowledge/graph services (stateless business logic)
- All UI tools (`CommonTools`, `MouseTools`, `KeyboardTools`, `ElementLocatorTools`, `UiElementDbTools`, `KnowledgeElementTools`,
  `SpinnerTools`, `VerificationTools`) — stateless
- All 11 UI LangChain4j agent proxies — stateless proxies
- Orchestrators (`StepExecutionOrchestrator`, `KnowledgeBasedExecutionOrchestrator`) — receive context via method params
- `ProcedureKnowledgeCollectionService`, `UiElementRefinementHelper`, `UiElementDialogHelper`, `ImageUtils`

Declares

### 3.4 Circular Dependency Resolution

`StepExecutionOrchestrator.promptUserAndDispatch()` calls `KnowledgeBasedExecutionOrchestrator.triggerEditProcedureFlow()` and
`triggerNewProcedureFlow()`, while `KnowledgeBasedExecutionOrchestrator.executeBasedOnKnowledge()` calls
`StepExecutionOrchestrator.executeAtomicStepWithRetryLoop()`. Direct mutual injection would create a compile-time cycle that avaje rejects.

**Resolution:** Extract both knowledge collection methods (`triggerNewProcedureFlow`, `triggerEditProcedureFlow`) from
`KnowledgeBasedExecutionOrchestrator` into a new `ProcedureKnowledgeCollectionService` `@Singleton`. Both orchestrators inject
`ProcedureKnowledgeCollectionService`. The dependency graph becomes:

```
StepExecutionOrchestrator  →  ProcedureKnowledgeCollectionService  ←  KnowledgeBasedExecutionOrchestrator
StepExecutionOrchestrator  ←  KnowledgeBasedExecutionOrchestrator   (one direction only — no cycle)
```

`ProcedureKnowledgeCollectionService` injects `KnowledgeSuggestionAgent` (directly — it is a `@Bean @Singleton` from `UiAgentsBeanFactory`), `KnowledgeService`, and `KnowledgeIngestionService` as constructor parameters.

### What Stays Manual (NOT DI-managed)

Only objects where multiple distinct instances with different configurations exist per request, value objects, or Swing EDT lifecycle
constraints remain manually created. Everything else is DI-managed (`@Singleton` or `@UiAgentRequestScope` / `@ApiAgentRequestScope`).

- **`DefaultToolErrorHandler` / `UiToolErrorHandler`** — multiple instances per request, each with a different `RetryPolicy` (one per
  agent). Cannot be singleton (different config) or request-scoped (multiple instances needed simultaneously)
- **`RetryState`** — embedded inside error handlers via `ThreadLocal`, multiple per request
- **`KnowledgeServices`** record — eliminated; individual services are injected directly
- **`ProcedureKnowledgeCollectionDialog`, `ExistingProcedureLookupDialog`** — Swing dialogs created on-demand on the EDT; receive config
  values as constructor parameters from DI-managed callers
- **`InheritanceAwareToolProvider`** — created per-agent inside `UiAgentsBeanFactory` `@Bean` methods (wraps injected tool singletons into a
  LangChain4j `ToolProvider`)
- **`DialogConfig`, `ProcedureDialogUIBuilder`, `ChildStepRowBuilder`, `SimilaritySearchTask`** — UI helper data carriers with
  per-invocation state
- **`BoundingBox`** — value object with per-instance coordinates
- **`PreconditionResolver`** — per-invocation helper created inside `executeBasedOnKnowledge()`

### Data Flow

1. `Server.main()` creates `BeanScope` with a shutdown hook
2. `BeanScope` auto-discovers all `@Singleton`, `@Factory` beans from both `agent_core` and the consuming module via generated `AvajeModule`
   service loader entries
3. `Neo4jFactory.driver()` initialises Neo4j `Driver`; `@PostConstruct` on `Neo4jFactory` triggers
   `SchemaMigrationManager.migrateOnStartup()`
4. Server retrieves `AbstractServer` bean → calls `start()` → Javalin binds routes
5. On task request: `AgentExecutionResource` → `UiAgentExecutor`/`ApiAgentExecutor` → `UiTestAgent`/`ApiTestAgent`
6. Agent creates a child `BeanScope` with `.modules(new BaseAgentRequestScopeModule(testCase), new UiAgentRequestScopeModule(visualState))` (UI)
   or `.modules(new BaseAgentRequestScopeModule(testCase), new ApiAgentRequestScopeModule())` (API). All request-scoped beans (`TestExecutionContext`,
   `UiTestExecutionContext`, `LogCapture`, `ScreenRecorder`, `ExecutionStateTracker`, `TestContextDataTools`, API tools, API agents) are
   auto-wired fresh per request. `@Singleton` beans (repositories, services, UI tools, UI agents, `BudgetManager`) are inherited from the parent scope
7. Request completes: child `BeanScope.close()` cleans up all request-scoped beans
8. On shutdown: parent `BeanScope.close()` → avaje calls `close()` on `Neo4jFactory` → `Driver` closed

## 6. Key Technical Decisions

1. **`AgentConfig` stays as a class hierarchy** — `UiTestAgentConfig extends AgentConfig` preserved, converted from static to instance.
   Minimises refactoring while gaining injectability.

2. **Per-request mutable state uses `@BaseAgentRequestScope` or `@UiAgentRequestScope` / `@ApiAgentRequestScope`** — `TestExecutionContext`,
   `LogCapture`, `TestContextDataTools` are `@BaseAgentRequestScope` (common to all agents, defined in `agent_core`). `UiTestExecutionContext`,
   `ApiContext`, `ExecutionStateTracker`, `ScreenRecorder`, API tools (`ApiRequestTools`, `ApiAssertionTools`), and API agents
   (`ApiTestStepActionAgent`, `ApiPreconditionActionAgent`) are module-specific request-scoped beans. Only objects needing multiple distinct
   instances per request (error handlers with different `RetryPolicy`), value objects (`BoundingBox`), and Swing dialogs stay manual.

3. **`BeanScope` owned by `main()` only** — each module's `Server.main()` creates one `BeanScope` for the application lifecycle.
   `shutdownHook(true)` ensures cleanup.

4. **`@InjectModule` for cross-module wiring** — `provides`/`requires` attributes declare cross-module bean dependencies; avaje validates
   wiring at compile time.

5. **`AbstractServer` becomes concrete `@Singleton`** — removes the template-method abstract pattern. `AgentExecutor` and `AgentCard`
   implementations are provided by each consuming module's `@Factory` beans and resolved by avaje at wire time through interface binding.
   `agent_core`'s `@InjectModule` must declare `requires = [AgentExecutor, AgentCard]` so avaje does not attempt to wire
   `AgentExecutionResource`'s interface dependencies within `agent_core` itself.

6. **Circular dependency resolved by extracting `ProcedureKnowledgeCollectionService`** — rather than using `Provider<T>` (which defers
   detection to runtime), extracting the shared knowledge collection methods (`triggerNewProcedureFlow`, `triggerEditProcedureFlow`) into a
   third class produces a clean acyclic object graph. `KnowledgeService` and `KnowledgeIngestionService` are injected as constructor
   parameters into `ProcedureKnowledgeCollectionService` (DI everywhere — not passed as method parameters).

7. **ALL LangChain4j agent proxies promoted to `@Bean @Singleton`** — inspired by langchain4j-cdi's approach of managing all AI service
   proxies as DI beans (see decision 22). All 11 agents (`UiStateCheckAgent`, `KnowledgeSuggestionAgent`, `UiElementResolutionAgent`,
   `UiTestStepVerificationAgent`, `UiPreconditionVerificationAgent`, `UiTestStepActionAgent`, `UiPreconditionActionAgent`,
   `UiElementBoundingBoxAgent`, `BestUiElementMatchSelectionAgent`, `UiElementExtendedDescriptionAgent`, `DbUiElementSelectionAgent`) become
   `@Bean @Singleton` beans produced by `UiAgentsBeanFactory`. Agent creation is centralized in `UiAgentsBeanFactory` rather than scattered across tool
   classes. Tool classes inject the agents they need as constructor parameters.

8. **`UiAgentsBeanFactory` injects only `ModelFactory` and `UiTestAgentConfig` in constructor** — injecting tool singletons (`CommonTools`,
   `MouseTools`, `KeyboardTools`, `ElementLocatorTools`, `UiElementDbTools`) into `UiAgentsBeanFactory`'s constructor would create a circular
   dependency: those tool classes inject `UiStateCheckAgent`, which is a `@Bean` produced by `UiAgentsBeanFactory` itself. To break the cycle, tool
   singletons are not constructor-injected into `UiAgentsBeanFactory`; instead, `@Bean` methods receive them as **method parameters** which avaje
   resolves independently from the constructor.

9. **No `EmbeddingStore<TextSegment>` bean** — `EmbeddingStore` is no longer used in the project. The `Neo4jFactory` produces only the
   `Driver` bean. No `Session` bean is produced — sessions are short-lived resources that callers open and close per operation via
   `driver.session(DatabaseConfig)`.

10. **`UiAbstractTools` refactored to constructor injection** — the no-arg constructor that internally creates `UiStateCheckAgent` via
    static calls is removed. All six subclasses (`CommonTools`, `MouseTools`, `KeyboardTools`, `ElementLocatorTools`, `UiElementDbTools`,
    `KnowledgeElementTools`) become DI-managed singletons and pass their injected `UiStateCheckAgent` to `super()`. `SpinnerTools` does not
    extend `UiAbstractTools` but is also a `@Singleton` bean — annotated for DI consistency so all tool classes are DI-managed.

11. **`VerificationTools` accesses `BudgetManager` via direct injection** — it calls `resetToolCallUsage()` and `getVerificationRetryPolicy()`,
    both of which are currently static imports. `resetToolCallUsage()` uses the injected `BudgetManager` instance; `getVerificationRetryPolicy()` uses the injected `AgentConfig` instance.

12. **`StepExecutionOrchestrator` accesses `BudgetManager` via direct injection** — it calls `resetToolCallUsage()` four times directly;
    both `BudgetManager` and `StepExecutionOrchestrator` are `@Singleton`, access is via `budgetManager.resetToolCallUsage()`.

13. **`ACTION_VERIFICATION_DELAY_MILLIS` is already sourced from `UiTestAgentConfig`** — `StepExecutionOrchestrator` already calls
    `getActionVerificationDelayMillis()` at field initialization time. After DI this becomes an instance field initialized from the injected
    config in the constructor.

14. **`UiElementDbTools` does not inject `UiAgentsBeanFactory`** — `UiElementDbTools` receives its internal agents (
    `UiElementExtendedDescriptionAgent`, `DbUiElementSelectionAgent`) as injected constructor parameters (the agents are `@Bean @Singleton`
    beans produced by `UiAgentsBeanFactory`). `UiAgentsBeanFactory` is NOT injected into `UiElementDbTools` — `UiAgentsBeanFactory` injects `UiElementDbTools`
    via `@Bean` method parameter, so injecting it back would produce a direct `A → B → A` cycle that avaje rejects at compile time.

15. **`UiAgentsBeanFactory` ↔ tool singleton circular dependency resolved by `@Bean` method parameter injection** — `UiAgentsBeanFactory` produces
    `UiStateCheckAgent` and all other agents as `@Bean @Singleton`; tool subclasses inject these agents. If `UiAgentsBeanFactory` also injected
    those tool classes in its constructor, avaje could not satisfy the dependency graph. The resolution: `UiAgentsBeanFactory` injects only
    `ModelFactory` and `UiTestAgentConfig` in its constructor; all `@Bean` methods that need tool singletons receive them as **method
    parameters** which avaje resolves independently.

16. **`@Bean` method parameter injection is the universal pattern for tool → agent → factory dependencies** — avaje injects parameters of
    `@Bean` producer methods at bean-creation time independently from the `@Factory` class constructor. This enables all agent `@Bean`
    methods to declare tool dependencies as method parameters without triggering circular dependencies with the factory's constructor.

17. **`AgentConfig` static field initializers must migrate into the constructor body** — Java instance fields cannot invoke instance methods
    in their initializers. All ~40 `ConfigProperty` assignments and the `Properties` loading must appear as sequential statements in the
    `AgentConfig` constructor. The `protected static` helper methods are converted to `protected` instance methods so that subclass
    constructors can call them after `super()` returns without triggering static-context issues.

18. **`BoundingBox` stays as a record — config passed as parameter** — while records CAN be `@Singleton` DI beans in avaje (compile-time
    code gen means `final` is not a problem; the canonical constructor serves as the injection point), `BoundingBox` is a value object
    holding coordinates — many instances are created with different data, so making it a singleton makes no sense. The
    `getActualBoundingBox()` method is refactored to accept a `boolean isAlreadyNormalized` parameter instead of calling
    `UiTestAgentConfig.isBoundingBoxAlreadyNormalized()` statically. Callers (which are DI-managed) pass the value from their injected
    config.

19. **Swing dialogs receive config as constructor parameters, not DI beans** — `ProcedureKnowledgeCollectionDialog` and
    `ExistingProcedureLookupDialog` are created on-demand in Swing EDT context. Making them DI beans is inappropriate. Instead, their
    callers (which are DI-managed `@Singleton` beans) pass the required config values and repository instances as constructor parameters.

20. **`UiElementRefinementHelper`, `UiElementDialogHelper`, and `ImageUtils` promoted to `@Singleton`** — these static utility classes call
    `AgentConfig`/`UiTestAgentConfig` static methods. After DI, they become `@Singleton` beans that inject the config instances. Their
    static methods become instance methods. All callers that are already DI-managed inject these helpers instead of using static calls.

21. **`AgentCardProducer` refactored to receive config as parameters** — both UI and API versions have a static field initialized from
    `AgentConfig.getExternalUrl()`. After DI, the external URL is passed as a parameter from the `@Factory` `@Bean` method that produces
    `AgentCard`, which injects `AgentConfig`.

22. **All LangChain4j agents as DI-managed beans — inspired by langchain4j-cdi** —
    the [langchain4j-cdi](https://github.com/langchain4j/langchain4j-cdi) library manages all `AiServices` proxies as CDI beans via
    `@RegisterAIService`. Since avaje-inject uses compile-time code generation (not CDI extensions), the equivalent pattern is: a `@Factory`
    class with `@Bean @Singleton` methods that call `AiServices.builder(...).build()`, with tools and models injected as `@Bean` method
    parameters. This approach centralizes all agent creation in `UiAgentsBeanFactory`, eliminates scattered `AiServices.builder()` calls across
    tool classes, and makes agent dependencies explicit and DI-validated at compile time.

23. **`TestCaseExtractionAgent` created once in `TestCaseExtractor` constructor** — the agent proxy is stateless and reusable. Rather than
    recreating it on every `extractTestCase()` call, it is built once in the constructor using the injected `modelFactory` and
    `agentConfig`, and stored as a `private final` field. This is consistent with the DI-everywhere principle: `TestCaseExtractor` is a
    `@Singleton`, and its agent is effectively an eagerly-initialized singleton within it.

24. **`BudgetManager` as Thread-Safe Singleton** — `BudgetManager` is a `@Singleton` that internally uses `ScopedValue`/`ThreadLocal` to track state per-request, replacing the need for it to be `@RequestScope`. Singleton beans inject it directly.

25. **Single request scope replaces ad-hoc child scopes** — the per-request child `BeanScope` in `UiTestAgent.executeWithKnowledgeFlow()`
    is eliminated. A single `BeanScope.builder().parent(appScope).modules(new BaseAgentRequestScopeModule(testCase), new UiAgentRequestScopeModule(new VisualState(captureScreen()))).build()`
    at the top of `executeTestCase()` provides all request-scoped beans. `BaseAgentRequestScopeModule` is wired first (provides `TestCase`,
    `TestExecutionContext`, `LogCapture`, `TestContextDataTools`); `UiAgentRequestScopeModule` is wired second and can inject beans from the
    base module. This ensures uniform lifecycle management — all per-request resources are created and cleaned up in one place.
